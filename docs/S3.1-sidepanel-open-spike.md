# S3.1 spike — can the app open the side panel?

**Status: implemented as try-with-fallback; needs a human verification pass in
real Chrome (the CI sandbox cannot exercise browser gesture semantics).**

## What is implemented (already on main since E4.3, kept)

`src/background/activeCase.ts` `handleExternalMessage`: on a valid
`SET_ACTIVE_CASE` from the allowlisted app origin, the worker best-effort calls
`chrome.sidePanel.open({ windowId })` for the sender's window inside
try/catch. When Chrome honours the gesture, the panel opens with the case in
hand; when it doesn't (no gesture context, older Chrome), the call throws
quietly and the toolbar icon remains the way in — the handoff record is stored
either way, so the panel picks the case up on next open ("picks up on focus",
the S3.5 criterion).

## What a human must verify (the actual spike deliverable)

On each target Chrome version (current stable, stable-1, and the org's oldest
deployed version):

1. In the webapp, click "Work in portal" on a case.
2. Record whether the side panel OPENED without another click.
3. If it did not, confirm the fallback: click the toolbar icon — the panel must
   open showing the handed-off case (no dropdowns).

## Copy rule until proven

Per the package (doc 06 C1): the webapp's launch copy must NOT promise the
panel will open. The panel-side `WorkInPortalButton` copy currently says the
portal tab opens and the extension picks the case up — that posture is safe
under either spike outcome. If verification proves auto-open across all target
versions, one follow-up story shortens both flows' copy.
